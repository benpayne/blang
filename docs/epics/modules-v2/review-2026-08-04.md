## (a) Verdict: **ready-with-amendments** — three amendments are blocking before `/devbot-plan`

The decision record (D1–D14) survives this review essentially intact — the
decisions are mutually consistent and well-argued, and every "today" claim I
checked reproduces against the code (appendix at bottom). But the **mechanism**
section over-claims in one load-bearing place (the "pointer-field finding"),
one acknowledged risk is actually a confirmed contradiction with a
done-condition bullet, and the unit ordering contains a real dependency
inversion. These are amendments to the plan sections, not teardowns of
decisions — hence not needs-rework — but findings 1–3 must land in the doc
before planning starts, because unit 4 as written cannot be implemented.

## (b) Findings, by severity

### F1 — CRITICAL: The construction/destruction ABI contradicts "drop layout from `.bmod`" (targets: "What actually crosses" pointer-field finding, Export model, unit 4, done bullet 2)

The doc's keystone claim — "struct-typed fields are stored as pointers... That
is what makes the export model possible **without opaque handles, ARC changes,
or codegen upheaval**" — is only half true. I verified fields-as-pointers
(`CGTypes.cpp:132-135`), but construction is **caller-allocating**: at a
`Counter(5)` site the *consumer's* codegen computes
`DataLayout::getTypeAllocSize(structType)` (`CGStruct.cpp:640-642`), generates
the struct's **destructor** via `getOrGenStructDestructor`
(`CGStruct.cpp:660` — which must walk the field list to release refcounted
fields), calls `__blang_rc_alloc_dtor(size, dtor)`, and only then calls
`StructName_init(heapPtr, args...)` (`CGStruct.cpp:667-668`). Without field
layout, the consumer can compute neither the size nor the dtor. The
pointer-field finding covers field *type identity* (an `Inner` field is one ptr
regardless of `Inner`'s shape) but not field *count and kinds* (`{string; int}`
vs `{int}` differ in size and in what the dtor releases).

**Amendment**: unit 4 must include a construction-ABI change, and it should be
the export model's early spike (ahead of, or alongside, the generics spike the
doc already flags). The clean fix, fully compatible with D1–D14: cross-module
construction goes through a **library-emitted factory** — the defining module
emits `StructName_new(args) -> ptr` (wrapping alloc-with-dtor + init), the
`.bmod` declares it, and the consumer's scope-exit release just calls
`__blang_rc_release`, which invokes the dtor pointer stored at allocation — no
layout needed on the consumer side. Alternatively keep layout in `.bmod` as
compiler-facing metadata (but that forfeits the advertised rebuild-avoidance
win and done bullet 2 as written). Either way, delete the "no ARC changes, no
codegen upheaval" sentence — it will mislead the architect.

### F2 — CRITICAL: table-struct and @json codegen *do* snag on private fields — the risk says "verify before unit 4"; I verified: it breaks (targets: Risks §3, unit 4, done bullet 2)

- `Sema::checkTableField` validates `.field` references against
  `StructDefinition::getFields()` in the **consumer's** compile
  (`Sema.cpp:578-620`); `SQLGen.cpp:277` reads `getFields()` for CREATE TABLE
  and column order; result-row mapping depends on "SELECT * column order ==
  struct field order" (CLAUDE.md Known Issues).
- `@json` generation builds `StructName_to_json/from_json` by walking fields
  in whichever module compiles the call (`CGRuntime.cpp:1519-1651`), and real
  consumer code calls generated functions **by name** —
  `examples/todo_app/main.b:160`: `Todo_from_json(req.body)`.

Under "no `.bmod` carries field layout," an imported `table struct` is
unqueryable and an imported `@json` struct unserializable. **Amendment**:
promote this from a "verify" risk to a decided design point, with two viable
resolutions the architect must choose between: (i) `.bmod` retains
compiler-facing field metadata that user source cannot resolve (visibility is
a resolution rule, not an emission rule — but done bullet 2 must be reworded,
see F9); or (ii) cross-module table/@json support routes through
library-exported generated functions declared in the `.bmod` (and the query
forms are restricted to the defining module). Also decide how a generated name
like `Todo_from_json` is spelled cross-module under D1 (`todos.Todo_from_json`?
`to_json`-style builtin dispatch?) — currently unaddressed.

### F3 — HIGH: Unit ordering bug — unit 6 reintroduces the bug unit 10 fixes (targets: units 6 and 10, sequencing)

Unit 6 "move[s] `cli` out of the promoted set into an ordinary qualified
module." But the code comment at `qcc.cpp:303-307` states `cli` was promoted
*precisely because* "a namespaced module's internal string-returning calls
(has_flag -> flag_name_of) hit a string-ARC double-free under the
module-prefix codegen." As sequenced (6 before 10), unit 6 ships that
double-free. **Amendment**: either pull the string-ARC root-cause fix forward
(it is a self-contained codegen bug fix with a `--leak-check` gate and no
dependency on any other unit — it could land second), or split unit 6 so the
`cli` demotion is explicitly deferred until after unit 10. I recommend the
former: the doc itself calls unit 10 "the crux"; a crux with no slack sitting
at position 10 of 13 is the epic's worst schedule risk, and nothing blocks
doing it early.

### F4 — HIGH: Protocol conformance never crosses the boundary — missing from all 13 units (targets: Proposed work units, Export model)

`BmodEmitter` emits protocol *definitions* (`BmodEmitter.cpp:302+`) but no
**conformance records** — `impl Printable for X` is never emitted for
non-generic structs (only generic structs ship an impl block, for bodies:
`BmodEmitter.cpp:238-261`). Consequences under the new model:
`print("{}", foreignValue)` (Printable dispatch), constraint checking for
`sort<T: Comparable>` with a foreign `T` (`stdlib/collections.b:261`), and
`impl ForeignProtocol for MyStruct` all fail cross-module. **Amendment**: add
"`.bmod` carries protocol-conformance records" to unit 2 or unit 5, with a
codegen E2E test (`print` of an imported Printable type) per constitution
Principle II.

### F5 — HIGH: Enums are absent from the export model (targets: Export model section, unit 3, done conditions)

The export model section is struct-only. Enum variants and payloads *are* the
API (and `BmodEmitter::emitEnum` ships them today), which is the exact
**inverse** of the struct rule — acceptable, but it must be stated, because
unit 3's "private type in an exported signature" enforcement must cover variant
payload types (same P9 mechanism), and D7 needs an enum ruling: matching a
foreign enum should be *use*-capability (patterns like `some(x)` never name
the enum — the subject's type carries it), while constructing
`mod.Enum.variant(x)` is *name*-capability. Also note the recursive-enum
boxing helpers (`__enum_<Name>_box_dtor`, `__enum_<Name>_payload_retain`) are
generated at use sites from variant layout — fine only if enums keep shipping
payload declarations in `.bmod`; say so. **Amendment**: add an "Enums"
paragraph to the export model and an enum fixture to units 3 and 5.

### F6 — MEDIUM: Cache keys do not include a format version — the risk item says "confirm"; confirmed absent (targets: Risks §7)

`BuildCache::computeKey` (`BuildCache.cpp:121-143`) hashes only source
contents + `blang.toml` + dep hashes. No compiler or `.bmod`-format version.
Since the `.bmod` format changes shape repeatedly in this epic, warm caches
will serve stale-format `.bmod`s and produce mid-epic mystery failures.
**Amendment**: convert the risk's "confirm cache keys incorporate a format
version" into a concrete task in unit 2 (the first format change): add a
format-version salt to `computeKey`.

### F7 — MEDIUM: D7's "var inference covers most consuming code" is overstated; boundary cases undecided (targets: D7, unit 5/8)

D7 is enforceable and nearly free to implement — if you can't name it,
resolution fails naturally; the real work is the diagnostic, which the risks
section correctly identifies. But: BLang has no function-signature inference
and lambda parameters are explicitly typed, so *any* refactor of consuming
code into a helper function or a lambda over a foreign type forces the import.
The rule stays coherent ("anything in a declaration needs the import") but the
doc oversells inference. Undecided boundary cases that need rulings in the D7
record before unit 8 writes fixtures: `?`/`match` on a foreign
`Result`/`Option` payload type (should be use); passing a foreign value into a
generic whose instantiation is inferred (should be use — the *compiler* names
the type, the source doesn't); `chan<T>` is moot (value types only, foreign
heap types already rejected). **Amendment**: soften the inference claim,
enumerate these cases in D7, and require a fixture per case in unit 8.

### F8 — MEDIUM: stdlib migration is API *design* work, not just churn (targets: Risks §2, unit 4)

Unit 4 says "migrate every consumer... onto `init`/accessors" and the risk
calls it mechanical. It isn't, for the stdlib:
`HttpRequest{method,path,body}` (`stdlib/net.b:190-194`), `HttpRequestLine`,
`HttpParsedHeaders` (parallel arrays), `FileInfo` are field-based DTOs with
**no accessors**, the non-goals explicitly ban generated accessors, and real
programs reach in (`examples/todo_app/main.b:146-147`: `req.path`,
`req.method`). Hand-writing the accessor surface for net/fs is a public-API
redesign, subject to constitution Principle I (docs in same change) and
Principle VI (design artifact first). **Amendment**: either carve a dedicated
unit "stdlib API accessor-ization" between units 2 and 4, or size it
explicitly inside unit 4 with its own design-audit checkpoint. Note also that
"module-visible private" must be enforced in `--combine` mode too (stdlib is
combined, not `.bmod`-mediated) — the doc's "unify the two paths" implies this
but no unit owns combine-mode visibility enforcement.

### F9 — MEDIUM: Done-condition sharpening (targets: Done condition)

The devbot manager evaluates these literally every turn. Most bullets are
behaviorally checkable; these need work:

- *"no `.bmod` carries field layout"* — contradicted by F1/F2 unless
  reworded. Propose: "field access on an imported type is a located error
  (fixture); any field metadata retained in `.bmod` (table/@json/ABI) is not
  resolvable from user source (fixture: naming the field fails even when
  metadata is present)."
- *"Resolution runs through a per-module graph; the up-front global-symbol
  injection is gone"* — code-structure claim, not artifact-checkable. Propose
  the behavioral form: "a program with two `.bmod` deps, only one imported:
  using the unimported dep's symbol is a located error (fixture under
  `test_build/`), and a same-named symbol exported by both resolves to the
  imported one."
- *"No hardcoded module exceptions remain in the driver"* — grep-shaped.
  Propose: "qualified `cli.has_flag` works and bare `has_flag` is a located
  error (fixtures); a new regression test `codegen_module_prefix_arc.b`
  exercises namespaced string-returning internal calls and is green under
  `--leak-check`."
- *"Type tiers... with a declared manifest"* — name the artifact path (e.g. a
  committed `stdlib/prelude.list` the driver reads) so the check is "file
  exists, driver consumes it, fixture proves a non-member requires
  qualification."
- *"Two modules exporting a same-named type coexist"* — add the check
  mechanism: "fixture with two path deps exporting the same type name;
  `llvm-nm` on the objects shows distinct mangled symbols; the linked binary's
  behavior test passes."
- *"blangd resolves imports..."* — good, but name the goldens: cross-module
  diagnostic, definition into the dep file, hover with the D3 display name,
  as `test_files/lsp/cross_module_*.expected.out`.
- Add a missing bullet: "warm-cache builds across a `.bmod` format change are
  correct (format-version salt in `BuildCache::computeKey`, with a test)."

## (c) The two open questions

**OQ1 — prelude membership**: Recommend exactly **{`Map`, `Set`, `Buffer`}**,
types only. Grounding: this is precisely today's force-promoted set minus
`cli`, so migration for these names is zero (as the doc anticipates). `Buffer`
has a *hard* argument beyond convenience: stdlib modules' own exported
signatures take `Buffer` (`stdlib/net.b:339`
`parse_http_request_line(Buffer buf)`, `net.b:65,72`) — if `Buffer` were
library-tier, every stdlib `.bmod` would need unit 5's foreign-type references
just to bootstrap, and every `net` user would need `import buffer` to write a
handler signature. Decide explicitly that the prelude is **types-only** for
v2: `sort` (`stdlib/collections.b:261`) becomes qualified `collections.sort` —
consistent with unit 6's `cli` reasoning ("free functions, not types").

**OQ2 — identity token for path deps**: Layer it. Keep `realpath` as the
**in-process** graph identity (D5 stands — `bcc.cpp:1049,1168` already
canonicalizes). But never serialize a raw absolute path into mangled symbols,
`.bmod` foreign references, or shareable cache keys: use a short digest (8–12
hex of SHA-256, infra already in-tree) of a **portable origin string** —
`url@pin` verbatim for git deps; for path deps, the path relativized to the
top-level project root when the dep lies inside the workspace, else the
realpath with reproducibility explicitly waived. This keeps symbols
readable-length, keeps machine paths out of binaries, makes the cache
shareable for the cases that matter (git deps, monorepos), and the
out-of-tree-absolute-path caveat is a deliberate simplification the
constitution (Principle VI) says to record in Known Issues. Note the
interaction the doc misses: `realpath` resolves symlinks, which is what makes
D6's "two paths are two modules" not fire spuriously on symlinked checkouts.

## (d) One epic or two

**Split, with the seam between the export model and the resolution graph —
but keep this document as the shared design record for both.**

- **Epic A — opaque exports**: units 2, 3, 4 (+ the F1 construction-ABI
  change), the F8 stdlib accessor unit, P9 enforcement, F6 cache versioning.
  Self-contained: it needs nothing from the resolution half, its done
  conditions are the first four bullets of the current list, and it has its
  own crux (the ABI spike).
- **Epic B — module graph**: units 1, 5, 6, 7, 8, 9, 10, 11 (+ stretch 12,
  13). Identity (unit 1) belongs here, not up front of everything: P10's
  `linkonce_odr` collapse only becomes *reachable* once two same-named types
  can coexist, which only Epic B enables — the doc's own "harmless today"
  concedes this.

Reasoning: the doc's "same problem seen from two sides" argument is correct
about *design* coherence — which is why D1–D14 should govern both — but it
doesn't follow that delivery must be one run. The merged epic has **two
independent critical-path cruxes** (construction ABI; string-ARC/module-prefix
codegen), 13+ units, and two large migration waves (field-access churn;
import-enforcement churn) — the classic split signal for a program where a
manager literally re-evaluates a done-condition list every turn. Two epics
give each a crisp, fully machine-checkable list and let Epic A ship
user-visible value (P8/P9 — the "critical" pain points users hit first) even
if Epic B's codegen crux slips. Sequence A before B, exactly as the doc
already argues visibility must precede resolution.

If the owner keeps it single, the current form is workable *only after*
findings F1–F3 are amended — F1 because unit 4 is unimplementable as written,
F2 because a done bullet is provably unsatisfiable alongside table-struct
support, F3 because the sequencing ships a known double-free.
